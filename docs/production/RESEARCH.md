# Production workflow research

**Accessed:** 2026-10-03
**Purpose:** Convert the production roadmap into an executable first release that gets a creator to a usable, upload-ready video quickly. Sources below are primary documentation, vendor-authored material, platform policy, or research papers. Vendor capability statements are not independent quality measurements.

## Recommendation

Ship a local, single-creator workflow that ends in a downloadable, manually uploaded MP4. Use dependable local durability from the outset: SQLite in WAL mode for records/jobs, a local content-addressed media vault, and a dedicated worker for long-running jobs. Do not wait for a full nonlinear editor, model training, managed/cloud infrastructure, multi-tenant architecture, or YouTube API integration. The shortest credible path is:

1. Turn the script into a shot list with one story beat, framing/action, dialogue/audio cue, duration, cast/wardrobe, location/props, and required reference per shot. Preserve exact dialogue separately from visual prompts.
2. Generate a small reusable visual bible: approved character front/three-quarter/full-body and expression/wardrobe views; style/color sheet; location and recurring-prop views. Treat it as guidance and provenance, not a model lock.
3. Produce a storyboard/animatic using stills, timing, scratch narration/music/SFX, and simple camera moves. Creator approves story, pacing, shot order and framing before spending on video.
4. Approve each shot’s still anchor and fingerprint. Generate short, independent clips from the approved shot anchor and canonical bible. Allow explicit first/last frames or timed keyframes only when supported. A new camera angle/location is a new shot and gets a fresh approved anchor. Do not automatically feed each output into the next shot.
5. Human reviews and accepts/rejects each take, then places chosen clips and audio in a simple local assembly timeline. Export MP4, play it back, inspect visual cuts and audio, and run file/duration/codec checks. Machine vision can flag likely defects; it cannot approve or release an anchor by itself. Explainable errors block or route to human review (never fail open); automated black/frozen-gap flags are advisory when the timeline annotates an intentional still, fade, or hold.
6. Present the finished file with a compact upload checklist. Creator uploads in YouTube Studio manually, selects audience, privacy and any applicable altered-content disclosure, and checks processed playback.

This keeps review before the costly step, makes individual failures replaceable, and gives the user a deliverable without building a general editor. A polished animatic is not the first public deliverable; it is an inexpensive planning and approval artifact. For the first release, a shot table plus generated stills and a basic local timeline can suffice if the user can still approve, reorder, retime, and replace material.

Keep provider and media work outside database transactions. Commit a small job/outbox state change with an idempotency key, do the provider request or file processing in the worker, then commit the result/status in a short transaction. SQLite cannot atomically commit remote provider effects or filesystem blobs with database rows; use content hashes, staged/atomic file placement, and restart reconciliation for orphaned files or pending jobs. This is an implementation recommendation inferred from the SQLite transaction boundary, not a guarantee provided by WAL.

## Release scope and gates

The first useful deliverable should be one finished local MP4, not an automated publishing service. Suggested release gate: a creator can import/write a script, edit a shot list, approve a cast/style reference and per-shot still, generate/select a take, add narration/music/SFX, reorder and retime shots, export a standards-based MP4, and manually review the whole file. Persist projects, revisions, approvals, job attempts and media metadata in SQLite WAL; persist bytes in the local content-addressed vault; and run generation/export in a dedicated worker that survives app restarts by recovering queued/leased jobs. Describe this as single-machine persistence with tested restart recovery, not as service redundancy or multi-host durability.

Human approval applies to the exact shot and reference revision reviewed. Any upstream script/cast/style/location change makes its affected shot anchors and approvals visibly stale. A model vision score may prioritize review but cannot override a missing, stale or rejected human decision. Errors, unreadable media and uncertain model scores go to a blocked/manual-review state.

Skip for this release: managed/cloud database, object store, queue and worker infrastructure; multi-user tenancy and cross-machine durability; automated upload/OAuth; full nonlinear editing; voice training; multi-minute continuous generations; and promises of identity-perfect output. The local database, vault and worker are part of the release, not later scalability work. Avoid dependencies that consume provider credits before the creator has approved the animatic and still anchors.

Before marking a video upload-ready, check: file opens and plays end-to-end; expected aspect/dimensions, frame rate and duration; no unexplained black/frozen gaps or accidental slate (intentional stills, fades and holds are timeline-annotated); dialogue is intelligible and music does not mask it; no clipping or missing audio; captions/title cards are inside the frame; exact final export is the file linked for download. Automated gap detection is a review hint, not an automatic failure when approved timeline intent explains the interval. YouTube still transcodes after upload, so creator should check the processed version and settings in Studio.
